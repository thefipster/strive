# Unified Wearable Data Platform — Design Specification

**Status:** Draft for implementation discussion
**Audience:** Coding agent + author (single developer/operator)
**Scope:** Personal, single-user system to ingest, catalog, parse, merge and report on wearable data from many vendors and formats.

---

## 1. Purpose & goals

Consolidate years of heterogeneous wearable exports (Polar, Garmin, Withings, Fitbit/Google, smartphone logs, manual logs, and older/custom devices) into a single, queryable, **fully traceable** dataset, and generate insight reports from it.

The data arrives as periodic export packages (ZIPs), taken every few months. The same logical file recurs across packages — sometimes unchanged, sometimes extended, sometimes new. The system must ingest incrementally, never redo work unnecessarily, and be able to **self-heal**: a bad parse is corrected simply by fixing the parser and re-running, with no manual cleanup.

### Primary goals
- Incremental, resumable ingestion of ~15 GB (uncompressed) of mostly text-based files (JSON, XML, CSV, INI-style, a few custom formats).
- Pluggable **classifiers** (identify what a file is) and **parsers** (extract data), auto-discovered via DI, executable and observable from a web UI. *(An early prototype with a few dozen classifiers/parsers already exists and should be migrated into this framework.)*
- A unified data model spanning two buckets — **daily data** and **training sessions** — each expressed as **metrics** and **series**.
- A **merge/fusion layer** that handles everything from clean temporal handovers to multi-source sensor fusion within a single training session.
- **Full provenance**: every stored value is traceable to the exact source file (by content hash) and parser/version that produced it. Provenance also drives conflict resolution.
- Pre-built reports and dashboards, generated by background jobs (no live/interactive analysis required).

### Non-goals (for now)
- Real-time or streaming analysis.
- Multi-user / multi-tenant / auth beyond a single trusted operator.
- Cracking every exotic format on day one (e.g. Withings BP-monitor EKG). These are explicitly deferred; the framework must let them be added later without disruption.

---

## 2. Deployment & runtime constraints

- **Single self-contained container**, deployed to a vanilla Docker / Portainer environment on Ubuntu.
- **Host:** Intel NUC, i5 (8 threads), 32 GB RAM, 1 TB PCIe SSD.
- No external database server should be *required* — the container should be self-sufficient. This constraint strongly favors **embedded** storage engines (SQLite, DuckDB) over a separate Postgres/Timescale service.
- Single OS process owns the data stores (the Blazor Server app hosts the background workers in-process), which conveniently sidesteps multi-writer concurrency problems.
- Stack: **.NET (latest LTS) + Blazor Server**.

---

## 3. Architectural principles

These five principles are the backbone. Everything else follows from them.

1. **Content-addressed, immutable raw layer.** Every file extracted from a ZIP is identified by the SHA-256 of its bytes. Identical files across packages collapse to one catalog entry — unchanged files cost nothing on re-import. Raw bytes are never mutated.

2. **Layered architecture, each layer rebuildable from the one above.**
   - **L0 – Raw**: content-addressed file blobs + per-package import manifests.
   - **L1 – Observations**: normalized metrics/series emitted by parsers, each stamped with full provenance. Append-only, but replaceable *by provenance key*.
   - **L2 – Canonical**: merged, deduplicated, conflict-resolved, sensor-fused view. **Derived** from L1 by versioned rules — never hand-edited.
   - **L3 – Reports/aggregates**: what dashboards read.
   - **Golden rule:** L1/L2/L3 can each be dropped and rebuilt from L0. That property *is* self-healing.

3. **Provenance on every record.** A compact `Provenance` reference (→ fileHash, parserId, parserVersion, runId, source locator/line) hangs off every observation and every canonical value. Any number in any report traces back to a byte range in a specific file.

4. **Determinism.** A parser/classifier/resolver at a fixed version produces identical output for identical input. This is what makes "delete by provenance and replay" safe.

5. **Self-healing via replay, not mutation.** Fixing data = fix code → bump version → invalidate affected work units → re-run. Old, still-good data is untouched; only the affected slice is rebuilt.

## 4. Pipeline stages

```
ZIP upload
   │
   ▼
[1] Ingest & unpack ──► L0 raw blobs (content-addressed) + import manifest
   │
   ▼
[2] Classify (detectors) ──► catalog entries tagged (vendor, dataType, candidate parser)
   │
   ▼
[3] Parse (streaming) ──► L1 observations (metrics + series) with provenance
   │
   ▼
[4] Group & fuse (resolvers) ──► L2 canonical (merged / conflict-resolved / sensor-fused)
   │
   ▼
[5] Report (background) ──► L3 aggregates ──► dashboards
```

Every stage is driven by a **job table** so it is resumable, observable in the UI, and re-triggerable when a version bumps.

### 4.1 Ingest & unpack
- Stream the uploaded ZIP to disk (do not buffer in memory; raise Blazor upload limits).
- Unpack; for each contained file compute SHA-256 → this is the **CatalogEntry** identity.
- Record an **ImportPackage** manifest: package id, upload timestamp, original archive hash, and the list of `(pathInArchive → fileHash)` mappings. The *same* fileHash can appear in many packages under many paths; store all such occurrences (path + package) but store the blob once.
- Deduplicate blobs by hash on write.

### 4.2 Classify (detectors)
- A **detector** looks at cheap signals — path, extension, magic bytes, a header peek — and proposes `(vendor, dataType, candidate parserId(s))` with a confidence.
- Classification is deliberately **separate** from parsing so it can run cheaply over everything and be re-run independently.
- Output: each CatalogEntry gets zero or more classification proposals. Ambiguous/unknown entries are flagged for the UI (this is where deferred/unknown formats surface).

### 4.3 Parse (streaming)
- A **parser** claims a specific `(vendor, dataType)` and streams observations out **one record at a time** (`IAsyncEnumerable<Observation>`), never loading whole files. Mandatory for large XML/TCX/GPX and multi-year series.
- Emits L1 observations with provenance = `(fileHash, parserId, parserVersion, runId, locator)`.

### 4.4 Group & fuse (resolvers) — see §7
- The non-trivial layer. Groups related L1 observations (esp. multi-source training sessions) and applies **fusion strategies** and **conflict resolution** to produce L2.

### 4.5 Report (background)
- Pre-built reports computed by background jobs over L2, materialized into L3. No interactive/live compute path required.

## 5. Data model

### 5.1 Buckets
Two bucket types share the metric/series structure:

- **Day** — keyed by calendar date (+ timezone). Holds daily metrics and full-day series (steps/min, HR/s, sleep periods…).
- **Session** — a training activity: `sport`, `startTime`, `endTime`, plus metrics and series. A session may be assembled from **multiple source files** (see fusion).

Both hang off a single **Subject** (the user). Subject is modeled explicitly even though there is one, to keep provenance/joins clean and future-proof.

### 5.2 Metrics and series
- **Metric** — one scalar fact for a bucket: `(bucketRef, metricTypeId, value, unit, provenanceRef)`. E.g. steps=8341, maxHr=182, totalDistance=10230 m, wakeTime=06:42.
- **Series header** — `(bucketRef, seriesTypeId, kind, unit, provenanceRef)` where `kind ∈ { Interval, Period }`.
- **Series points**:
  - **Interval** → `(seriesId, timestamp | offsetFromStart, value)`. For truly regular sampling, store `startTime + sampleRate + value[]` to save space. **RR intervals are the exception**: they are irregular by nature (one value per heartbeat), so store `(timestamp, rrMillis)` or `(cumulativeTime, rrMillis)`.
  - **Period** → `(seriesId, from, to, label|value)`. E.g. "device worn 06:00–23:10", "REM 02:14–02:47".

### 5.3 Controlled vocabularies (load-bearing)
- **MetricType / SeriesType**: a curated, vendor-independent vocabulary (`steps`, `hr_instant`, `rr_interval`, `distance`, `sleep_stage`, `speed`, …). This vocabulary is what makes cross-vendor comparison possible. Vendor-specific fields map *into* it during parsing.
- **Units**: canonical unit per type; normalize on ingest (Garmin semicircles → degrees; cm/m; kcal/kJ; m/s vs km/h). Store canonical unit on every observation.

### 5.4 Provenance model
- **Provenance** table: `(id, fileHash, parserId, parserVersion, runId, sourceLocator)` where `sourceLocator` is a format-appropriate pointer (line number, XPath, byte offset, JSON pointer).
- Every L1 observation references exactly one Provenance row.
- **L2 canonical values carry lineage too**: a canonical value references the L1 observation(s) and the **resolver + resolverVersion** that produced/selected it. So a fused or chosen value is as traceable as a raw one.

### 5.5 RR-interval volume note (drives storage)
Every heartbeat over years → order **50–100k rows/day**, i.e. **tens to 100+ million rows** total. Trivial for columnar Parquet (a few hundred MB to low-GB compressed), painful for row-store scalar tables. This is the dominant sizing factor — not the 15 GB of source. Design storage around it.

## 6. Storage design

Given the single-container constraint and RR volume, use a **two-store split**, both embedded:

### 6.1 Operational / metadata store — **SQLite** (via EF Core)
Holds everything transactional and small-write-heavy:
- L0 catalog (CatalogEntry, ImportPackage, blob index)
- Job table & orchestration state
- Parser/classifier/resolver registry & versions
- Provenance rows
- Metric scalars (L1 + L2 canonical scalars)
- Session/Day bucket records, MetricType/SeriesType vocabularies
- Report metadata (L3 index)

SQLite is transactional, robust for the many small writes the job engine makes while reports read, and fully embedded.

### 6.2 Analytical / high-volume series store — **Parquet + DuckDB**
Holds L1/L2 **series points**, especially RR intervals:
- Store series as Parquet, partitioned by `seriesType / subject / year` (RR partitioned finer, e.g. by month).
- Query with **DuckDB.NET** for aggregates and report building; DuckDB reads Parquet directly and is columnar/vectorized — ideal on this hardware.
- Rebuilding L2/L3 series can be expressed largely as SQL over Parquet.

### 6.3 Blob store
- L0 raw blobs on the SSD filesystem, path = sharded by hash prefix (`ab/cd/abcd…`). The SQLite catalog indexes them.

### 6.4 Single-writer discipline
The Blazor app process owns both stores. Background workers are in-process. This avoids DuckDB's single-writer limitation and SQLite lock contention becoming a problem. If workers are ever moved out-of-process, revisit this.

*(Alternative considered: Postgres + TimescaleDB. Rejected as the default because it violates the "single self-contained container" constraint and adds an operational service for no gain at single-user scale. Keep as a future option only if concurrency needs change.)*

## 7. Merge / Fusion layer (the hard part)

Merging is **not** appending. Multiple sources make competing or complementary claims. Keep all claims in L1; compute L2 by **explicit, versioned resolvers**. Below is the taxonomy the system must support, derived from real cases.

### 7.0 Prerequisite: session identity / grouping
Before session fusion can happen, the system must decide **which source files belong to the same training session**. Implement a **grouping step** that clusters session-scoped L1 observations by overlapping time windows (and sport hints where available), producing candidate **SessionGroups**. Fusion strategies operate on a SessionGroup. Grouping must be reviewable/overridable in the UI, because near-simultaneous activities and clock drift make it occasionally ambiguous.

### 7.1 Type A — Temporal handover (non-overlapping sources)
*Example: Polar until 2024-03-23, Fitbit/Google until 2025-06-14, then Polar again.*
- Sources cover **disjoint** time ranges for the same metric/series type.
- Resolver simply **stitches** by time into one continuous canonical series. Clean merge.
- Watch for small overlaps at the seams and duplicated boundary days → dedup by `(type, timestamp, source)` and prefer a configured source in the overlap.

### 7.2 Type B — Competing overlapping daily data
*Example: Garmin sleep vs Polar sleep for the same nights.*
- Both sources claim the same fact over the same period.
- **Do not collapse destructively.** Keep both in L1. L2 exposes a **source-priority selection per metric type** (e.g. "for sleep, prefer Garmin"), and reports may **override** the selection ("compare Garmin vs Polar sleep", or "use Polar sleep for this report").
- Requirement: canonical layer must support *both* a default choice **and** per-report source selection, with full lineage so a report says which source each value came from.

### 7.3 Type C — Session fusion by time synchronization
*Example (ancient watches): HR + timing INI from an old Polar watch + GPS + timing CSV from a smartphone, both for one run.*
- Complementary series (HR from one device, GPS from another) for the same session.
- Both share a **common start**; resolver **synchronizes start times** (with a small configurable offset correction) and **matches samples by aligned time**, producing one session with HR + GPS series on a common clock.
- Straightforward once start alignment is fixed.

### 7.4 Type D — Session fusion by distance registration (the involved one)
*Example: one source has HR + Speed (from an inertial reference system) + time; a separate GPS file has **only the track** (positions, unreliable/absent timing). Goal: attach GPS position to each HR/speed time sample.*

Because the GPS timing can't be trusted, align on **distance**, not time:

1. **Distance from the speed log** — integrate speed over time: `d_speed(t) = ∫ v dt`, computed as cumulative trapezoidal integration over the (time, speed) samples. *(Note: this is numerical **integration** of speed → distance, not differentiation.)*
2. **Distance from the GPS track** — cumulative geodesic distance: sum of haversine (or Vincenty) distances between consecutive track points → `d_gps` as a function of track index.
3. **Normalize / reconcile** — the two total distances will differ (GPS noise, IRS drift). Scale/warp one distance axis onto the other (at minimum a linear scale to equalize totals; better, a monotonic alignment / lightweight DTW on the cumulative-distance curves).
4. **Register & join** — for each HR/speed time sample, take its `d_speed`, map through the reconciliation to a GPS cumulative distance, and interpolate the GPS position at that distance. Result: lat/lon attached to every time sample.
5. Emit the fused session (HR, speed, position, derived distance) to L2 with lineage to both source files **and** the resolver+version (so the fusion itself is reproducible and correctable).

### 7.5 Resolver interface (unifying A–D + conflict resolution)
- Resolvers are **pluggable, DI-discovered, versioned** — structurally like parsers but operating at L1→L2.
- A resolver declares what it consumes (metric/series types, bucket type, applicability predicate over a SessionGroup or day) and emits canonical observations **with lineage**.
- Bumping a resolver version invalidates and recomputes only the L2 it produced (see §8).
- Source-priority tables and per-report source selection are configuration consumed by resolvers/reports, versioned alongside them.

## 8. Self-healing mechanics

The property that makes the whole thing robust. Concretely:

- **Work units are keyed and versioned.** A parse unit = `(catalogEntryId, parserId)`; it records the `parserVersion` and `runId` that last succeeded. A fusion unit = `(sessionGroupId | dayId, resolverId)` similarly.
- **Version bump ⇒ staleness.** When a parser/classifier/resolver version increases, all work units bound to it become **stale** and re-queue automatically.
- **Replace by provenance, never mutate.** Re-running deletes all L1 (or L2) rows whose provenance = `(fileHash, parserId, oldVersion)` and inserts the new output. A crash mid-run leaves the old good data until the new run commits (transactional swap).
- **Invalidation cascade.** L1 change → invalidate dependent L2 (via lineage) → invalidate dependent L3 reports. Cascade is driven by the lineage links, so it's precise (only affected slices rebuild).
- **Full rebuild is always possible** from L0 (disaster recovery / big refactors).

---

## 9. Orchestration & jobs

- **Job table** (SQLite): `(id, kind, targetKey, code+version, state, attempts, error, timings)` with `state ∈ pending|running|succeeded|failed|stale`.
- **Background processing** via a hosted `BackgroundService` reading a bounded `Channel<Job>` (consider Hangfire/Quartz only if durable retry/scheduling beyond this is wanted). Parallelism tuned to the 8-thread host.
- **Never tie long work to the SignalR circuit** — closing the browser tab must not kill a multi-GB run.
- **Progress** streamed to the UI from the job table over the circuit; the "parsers/resolvers list + run/status" UI is just a live view of that table.
- Resumability: on startup, re-enqueue `running` (interrupted) and `stale` units.

## 10. Blazor Server application

- **Upload**: drag-drop ZIP, streamed to disk, unpack in background; show per-package ingest progress.
- **Catalog view**: browse CatalogEntries, filter by vendor/dataType/classification/unknown; inspect provenance and the packages a blob appeared in.
- **Classifiers & parsers**: list DI-discovered components with versions; run/re-run against selected catalog entries or whole classes; show job status.
- **Resolvers / fusion**: review SessionGroups, override grouping, run fusion strategies, inspect competing-source situations, set source priorities.
- **Dashboards**: read L3; charts for daily metrics, training sessions, HRV/RR-derived metrics, source comparisons. *(When building any chart, follow the project's dataviz conventions.)*
- **Provenance drill-down**: from any displayed number, navigate to the exact source file + locator.

---

## 11. Reporting (L3)

- Pre-built reports generated by background jobs over L2; no interactive compute path required.
- Each report records the L2 lineage + report code version it was built from, so reports are reproducible and invalidated correctly when upstream data heals.
- Support **source-parameterized** reports (Type B): the same report can be built against different source selections (e.g. Garmin-sleep vs Polar-sleep) and labeled accordingly.

---

## 12. Deferred / unknown formats

- **Withings BP-monitor EKG** and any remaining custom/binary blobs: classified and cataloged, but parsing deferred. They sit in L0 with an "unparsed/unknown" flag and surface in the UI. Adding a parser later triggers normal processing with no disruption to existing data.
- Keep a visible "unknown/unclassified" queue so coverage gaps are always apparent.

---

## 13. Suggested build order

1. **L0 core**: upload → unpack → content-addressed catalog + import manifests (SQLite + blob store). Prove dedup across two real packages.
2. **Job engine + background service** with the job table and UI status view.
3. **Classifier + parser framework** (interfaces, DI discovery, versioning, streaming, provenance). Migrate the existing prototype classifiers/parsers into it.
4. **L1 storage**: metrics in SQLite, series in Parquet/DuckDB; wire provenance end-to-end; validate on RR-interval volume.
5. **Self-healing loop**: version bump → staleness → replace-by-provenance → verify a fixed parser corrects data with no manual cleanup.
6. **Fusion layer**: SessionGrouping, then resolvers for Type A → B → C → D in that order of difficulty. Source-priority config + per-report source selection.
7. **Reporting + dashboards** (L3), including source-comparison reports.
8. **Deferred formats** as parsers are written.

## 14. Open questions for the coding agent / next discussion

1. **Series storage detail for RR**: cumulative-time vs absolute-timestamp keys; partition granularity; whether to also persist derived HRV metrics as L1 or compute on report.
2. **SessionGroup matching**: exact time-window overlap tolerance and clock-drift correction defaults; UI override model.
3. **Type D registration**: is a linear distance-scale reconciliation sufficient, or is monotonic warping/DTW needed for your worst GPS/IRS deviations? (Affects effort significantly.)
4. **Source-priority configuration**: static per-metric-type config vs time-ranged rules (priorities may change as devices change).
5. **Report parameterization**: how far to push per-report source selection into a general mechanism vs bespoke reports.
6. **EF Core + DuckDB.NET boundary**: cleanest way to keep the two stores consistent under the invalidation cascade (transaction spanning both is not atomic — define the commit/rollback ordering).
7. **Prototype migration**: shape of the existing classifiers/parsers vs the interfaces here — adapter layer or rewrite?

## 15. Glossary

- **CatalogEntry** — a content-addressed raw file (identity = SHA-256 of bytes).
- **ImportPackage** — one uploaded ZIP and its `path→hash` manifest.
- **Observation** — a single metric or series datum with provenance (L1).
- **Bucket** — a Day or a Session; owns metrics and series.
- **Metric** — a scalar fact for a bucket.
- **Series** — an ordered set of points; `Interval` (sampled values) or `Period` (from–to spans).
- **Provenance** — link from a value to `(fileHash, parser/resolver, version, run, locator)`.
- **Resolver** — versioned component that computes L2 canonical data from L1 (merge / conflict resolution / sensor fusion).
- **SessionGroup** — cluster of source files judged to belong to one training session.
- **Self-healing** — correcting data by fixing code + version bump + replay, never by manual mutation.
